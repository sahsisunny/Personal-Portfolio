When we set out to build an AI chatbot agent backend on top of our existing property management services at Fountane, the initial product pitch sounded deceptively straightforward: connect an LLM to internal microservices so front-desk staff can query reservations, generate room audit summaries, and resolve guest issues in plain English.

In reality, orchestrating **200+ REST APIs** through an LLM exposes every hidden edge case in your backend architecture. 

Here is what broke first in production, the data discrepancies we uncovered, and how we re-architected the system in Go.

---

### Executive Summary

| Problem Encountered | Root Cause | Engineering Solution |
| :--- | :--- | :--- |
| **Context Window Bloat** | Passing 200+ tool schemas consumed 18k tokens per call. | Two-stage routing: High-level intent classifier narrows tools to 8–12. |
| **"Yesterday" Timezone Drift** | LLM defaulted to server UTC instead of hotel IANA timezone. | Explicit datetime boundary injection (`start_time`, `end_time`) in runtime context. |
| **Privilege Escalation** | LLM hallucinated invocations to restricted admin endpoints. | Strict Go-level RBAC middleware and JWT claims validation before execution. |
| **Unbounded Microservice Latency** | Sequential API calls caused 8s+ response times. | Concurrent Go worker pools with `context.WithTimeout` and circuit breakers. |

## 1. Tool Selection Bloat & Token Degradation

In early prototypes, developers often dump all available OpenAI/Anthropic function declarations into the system prompt. With 200+ endpoints, this created three immediate problems:

1. **Token Cost & Latency:** Tool schemas alone consumed ~18,000 tokens before the user even typed "Hello", inflating prompt latency to over 3.8 seconds.
2. **Hallucinated Parameters:** Models suffered from "attention dispersion"—confusing query parameters between similarly named endpoints (e.g., `/v1/reservations/lookup` vs `/v1/guest/reservations/history`).
3. **Selection Errors:** The LLM picked the wrong tool 14% of the time on ambiguous operator queries.

### The Solution: Two-Stage Domain Routing

Rather than exposing all 200 tools at once, we decoupled the agent into a lightweight **Semantic Intent Classifier** followed by an **Execution Agent**:

```
+-------------------------------------------------------------------------+
|                          Front-Desk Operator                            |
|                 "Check out Room 402 and bill the minibar"               |
+------------------------------------+------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|                  Stage 1: Intent & Domain Classifier                    |
|             (Ultra-fast prompt, returns: DOMAIN_HOUSEKEEPING,           |
|                       DOMAIN_BILLING, DOMAIN_FRONTDESK)                 |
+------------------------------------+------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|                 Stage 2: Dynamic Tool Sub-Registry                      |
|           Filters 200+ tools down to 8-12 relevant endpoints            |
|         [RoomStatusUpdate, PostFolioCharge, GenerateFolioPdf]           |
+------------------------------------+------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|                  Stage 3: Go Agent Execution Engine                     |
|           • Validates RBAC permissions for acting employee              |
|           • Executes HTTP REST microservice calls concurrently          |
|           • Verifies responses against Go struct schemas                |
+-------------------------------------------------------------------------+
```

### Go Implementation: Domain Sub-Registry & Dispatcher

Here is how our Go backend registers tool namespaces and dynamically constructs tool payloads based on classified intent:

```go
// agent/dispatcher.go
package agent

import (
	"context"
	"fmt"
	"time"
)

type Domain string

const (
	DomainReservations Domain = "RESERVATIONS"
	DomainBilling      Domain = "BILLING"
	DomainHousekeeping Domain = "HOUSEKEEPING"
	DomainGuests       Domain = "GUESTS"
)

type ToolDefinition struct {
	Name        string                 `json:"name"`
	Description string                 `json:"description"`
	Domain      Domain                 `json:"domain"`
	Parameters  map[string]interface{} `json:"parameters"`
	RequiredRole string                `json:"required_role"`
}

type AgentDispatcher struct {
	registry map[Domain][]ToolDefinition
}

func NewAgentDispatcher() *AgentDispatcher {
	return &AgentDispatcher{
		registry: make(map[Domain][]ToolDefinition),
	}
}

// ResolveToolsForIntent returns only the 8-12 tools required for the task
func (d *AgentDispatcher) ResolveToolsForIntent(
	ctx context.Context, 
	userRoles []string, 
	domains ...Domain,
) ([]ToolDefinition, error) {
	var authorizedTools []ToolDefinition

	for _, dom := range domains {
		tools, exists := d.registry[dom]
		if !exists {
			continue
		}

		for _, t := range tools {
			// Enforce RBAC filtering before schema ever reaches LLM context
			if hasRequiredRole(userRoles, t.RequiredRole) {
				authorizedTools = append(authorizedTools, t)
			}
		}
	}

	if len(authorizedTools) == 0 {
		return nil, fmt.Errorf("no authorized tools available for domains: %v", domains)
	}

	return authorizedTools, nil
}
```

## 2. The "Yesterday" Ambiguity: Timezone Drift

One of the most insidious bugs discovered during our production audit was date-window calculation.

When a front-desk night auditor asks:
> *"Show me all checked-out rooms from yesterday."*

Different underlying microservices expected different inputs:
* The **Housekeeping API** expected UTC ISO-8601 timestamps (`2026-10-14T00:00:00Z`).
* The **Billing API** expected the property's local midnight-to-midnight window.
* The **Reporting Service** expected raw date strings (`YYYY-MM-DD`).

When left to the LLM, the model would invoke standard UTC `time.Now()`. If the server was hosted in AWS `us-east-1` (UTC-4) while the hotel was located in London (UTC+1) or Tokyo (UTC+9), "yesterday" shifted by an entire calendar day, returning zero records or corrupted revenue numbers.

### The Fix: Pre-Computed Temporal Envelopes

We stripped the LLM of relative calendar math. Instead, our Go middleware calculates explicit temporal boundaries in the hotel's IANA timezone and injects them directly into the runtime context:

```typescript
// agent/context-builder.ts
export interface HotelRuntimeContext {
  propertyId: string;
  propertyTimezone: string; // e.g., "Asia/Kolkata" or "Europe/London"
  currentTimeLocal: string;
  calculatedWindows: {
    todayStartLocal: string;
    todayEndLocal: string;
    yesterdayStartLocal: string;
    yesterdayEndLocal: string;
    currentShiftStartLocal: string;
  };
}

export function buildTemporalEnvelope(timezone: string): HotelRuntimeContext["calculatedWindows"] {
  const now = new Date();
  // Compute exact midnight boundaries in property's timezone
  const localToday = new Intl.DateTimeFormat("en-CA", { timeZone: timezone }).format(now);
  
  return {
    todayStartLocal: `${localToday}T00:00:00`,
    todayEndLocal: `${localToday}T23:59:59`,
    yesterdayStartLocal: computeRelativeDate(localToday, -1, "00:00:00"),
    yesterdayEndLocal: computeRelativeDate(localToday, -1, "23:59:59"),
    currentShiftStartLocal: computeCurrentShift(now, timezone),
  };
}
```

Now, the prompt instruction reads:
```
Property Timezone: Asia/Kolkata
Target 'yesterday' range: 2026-10-14T00:00:00+05:30 to 2026-10-14T23:59:59+05:30
NEVER guess UTC timestamps. Use the provided ISO boundaries for date-range tool queries.
```

## 3. Privilege Escalation & Audit Trail Hardening

Because hotel front desks operate in shift rotations (morning, evening, night audit), employees have different security clearances. A trainee front-desk clerk should be able to view room status, but must never be allowed to trigger a manager cash-drawer reconciliation or override rate codes.

We implemented **Three-Tier Defense-in-Depth**:

1. **Prompt Isolation:** Unauthorized tools are completely omitted from the schema sent to the LLM.
2. **Go Middleware RBAC Verification:** Even if the LLM attempts to invent an API call, our dispatcher verifies the employee's JWT claims against the tool's required role before firing any HTTP request.
3. **Immutable Audit Logging:** Every executed tool, its raw input parameters, execution duration, and caller identity are written directly to PostgreSQL.

```sql
-- Security audit query: Inspecting all high-privilege agent invocations
SELECT 
    l.id,
    l.employee_id,
    l.property_id,
    l.tool_name,
    l.parameters->>'room_number' AS room,
    l.execution_duration_ms,
    l.status_code,
    l.created_at
FROM agent_audit_logs l
WHERE l.tool_name IN ('OverrideRoomRate', 'ForceCheckOut', 'IssueFolioRefund')
  AND l.created_at >= NOW() - INTERVAL '24 hours'
ORDER BY l.created_at DESC;
```

## What We Learned

1. **LLMs should never do calendar math:** Always calculate time boundaries, shift windows, and fiscal dates deterministically in backend code before passing them to the model.
2. **Dynamic sub-registries are mandatory at scale:** If your agent has more than 15 tools, a single-stage prompt will degrade. Classify intent first, then load domain tools.
3. **Never trust LLM tool parameters implicitly:** Always validate types with Zod or Go struct tags (`validator/v10`) before sending the payload over the wire to your internal microservices.

Our next engineering milestone introduces **Agent Routines**: long-running scheduled automations that trigger morning room audits, flag rate discrepancies across booking channels, and request human-in-the-loop sign-off before executing financial adjustments.
